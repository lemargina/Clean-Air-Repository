# CODEX TASK — Clean Air Finder Bulgaria

## Role

Act as a senior Laravel backend engineer, database architect, DevOps engineer and QA engineer.

Build a complete, production-ready application called **Clean Air Finder Bulgaria**.

Do not stop at architecture recommendations. Implement the application, database migrations, services, scheduled jobs, frontend, tests, documentation and deployment configuration.

Use real publicly available environmental measurements. Do not use mock data in production.

Work autonomously, but document important decisions and limitations.

---

# 1. Business requirements

The application must answer:

**Which Bulgarian city had the cleanest air during a selected historical period?**

The user selects two dates using a calendar:

- Date From
- Date To

After clicking **Find Cleanest Air**, the application must display:

1. The Bulgarian city with the lowest average PM2.5 concentration.
2. Average PM2.5 in µg/m³.
3. Average PM10 in µg/m³ as supplementary information.
4. Number of sensors contributing to the result.
5. Number of valid measurement days.
6. Data coverage percentage.
7. The selected period.
8. Measurement source and last successful synchronization.
9. A ranking of all eligible cities.
10. A clear explanation of how the result was calculated.

Use PM2.5 as the primary ranking metric. Do not combine PM2.5 and PM10 into an arbitrary composite score.

Explain that the result represents measured particulate concentrations, not a comprehensive air-quality or health assessment.

Cities with insufficient data must not qualify as winners.

# 4. Data collection

Implement automatic collection every 15 minutes using Laravel Scheduler.

Example scheduled command:

`php artisan air:collect`

Requirements:

- Fetch Bulgarian particulate sensor data.
- Validate HTTP responses.
- Parse JSON safely.
- Extract PM2.5 and PM10.
- Extract sensor ID, location ID, timestamp, latitude and longitude.
- Reject invalid geographic coordinates.
- Reject negative or non-finite measurements.
- Flag suspicious readings using documented quality rules.
- Use source measurement timestamps, not ingestion timestamps, for historical calculations.
- Store raw measurements locally.
- Prevent duplicates using database unique constraints.
- Use batch inserts/upserts.
- Use request timeouts.
- Implement retries with exponential backoff for temporary failures.
- Respect HTTP 429 and Retry-After.
- Prevent concurrent collection runs using locking.
- Log failures without crashing the application.
- Record collection duration, processed count, inserted count, duplicates, invalid records and source status.

One failed collection must not damage previously stored measurements.

Do not assume that requesting the same live snapshot every 15 minutes yields exactly one new observation per sensor.

# 5. Historical backfill

The application must contain at least 12 months of real historical data.

A newly deployed installation must be capable of downloading historical data instead of waiting 12 months.

Implement:

`php artisan air:backfill --months=12`

Requirements:

- Download historical measurements from Sensor.Community archives.
- Support their actual published CSV or Parquet layout.
- Process historical data in chunks or streams.
- Avoid loading large archives entirely into PHP memory.
- Be restartable.
- Store progress and checkpoints.
- Avoid duplicate measurements.
- Retry failed archive downloads later.
- Validate downloaded data.
- Support interrupted imports.
- Record source files, processing status and errors.
- Allow importing a specific date range.

Example:

`php artisan air:backfill --from=2025-10-01 --to=2026-10-01`

Do not claim that 12 months of history exist until the backfill has actually completed and coverage has been verified.

The backfill must be practical for the full Bulgarian dataset, not just a few manually selected sensors.

# 6. Bulgarian cities and geographic assignment

Measurements contain coordinates, not necessarily trustworthy city names.

Create a reliable local geographic dataset for Bulgarian settlements.

Investigate suitable sources such as:

- Official Bulgarian geographic or statistical datasets.
- OpenStreetMap.
- GeoNames.
- Openly licensed administrative boundaries.

Verify licensing and attribution.

Store at minimum:

**cities**
- id
- name_bg
- name_en, when available
- latitude
- longitude
- municipality
- region
- population, when available
- external_identifier
- geographic_source

**sensors**
- id
- external_sensor_id
- external_location_id
- sensor_type
- latitude
- longitude
- city_id
- assignment_method
- assignment_distance_km
- first_seen_at
- last_seen_at
- is_active

Prefer polygon-based settlement assignment when suitable settlement boundaries are available.

Otherwise implement nearest-city assignment using the Haversine formula or PostGIS.

Use a configurable maximum distance, initially 10 km, and document it.

Do not assign a remote rural sensor to a city merely because that city is geographically nearest.

Sensors that cannot be assigned confidently must remain unassigned.

Handle sensors changing location over time. Historical measurements must preserve their correct geographic association.

A coordinate located outside Bulgaria must not be accepted as a Bulgarian sensor solely because the API country filter returned it.

## Performance

Historical queries must not scan every raw measurement.

Implement daily aggregations and appropriate database indexes.

Suggested flow:

Raw measurements → Sensor daily statistics → City daily statistics → Historical ranking.

Aggregation must preserve sample counts and temporal coverage.

Avoid bias where sensors with more frequent reporting dominate the city average.

For a city-period comparison, use a documented approach based on sensor-hour observations, sensor-day aggregates and city-day aggregates.

Handle missing readings and irregular reporting.

Never average precomputed daily averages blindly when they represent different numbers of valid observations, unless this weighting is an explicit methodological choice.

Ensure that aggregation updates are idempotent and can be recomputed after late historical imports.

# 8. Cleanest city calculation

Implement a dedicated service, for example:

`App\Services\AirQuality\CleanestCityService`

Input:

- date_from
- date_to

Output:

- Winning city.
- Average PM2.5.
- Average PM10.
- Days covered.
- Number of contributing sensors.
- Data coverage percentage.
- Complete eligible ranking.
- Excluded cities and reasons.
- Source attribution.
- Calculation methodology.

Default qualification rules:

- Minimum 75% valid calendar-day coverage.
- Minimum 1 qualifying sensor.
- Sensor-day and hourly completeness thresholds must be defined and documented.
- Cities with no qualifying observations must be excluded.

Avoid giving an artificial advantage to a city with only a few unusually clean measurements.

For periods with a single day, use explicit hourly coverage criteria.

When multiple cities tie, return all tied cities or use an explicitly documented deterministic tie-breaking rule.

Implement the calculation using indexed local database data only.

No external API calls are permitted during a user's historical search.
